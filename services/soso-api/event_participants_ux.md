# UXフロー（参加→ドライバー方向）とDB状態の対応

## 目的
「参加者」「行きドライバー（迎え）」「帰りドライバー（送り）」「両方」をDB上で破綻なく表現しつつ、フロントのボタン選択回数を最小にする。

業務ルール（前提）として、ユーザーがドライバーを選んだ場合でも、最終的に成立しうる状態は以下の **4状態**に制限されるUXとする。

## 状態（4通り）
DBは 1人=1行で `*_status` 列を持つ想定（未登録は `NULL`、登録/無効化は `ENUM('registered','cancelled')`）。

| UX上の意味 | participant_status | go_driver_status | return_driver_status |
|---|---|---|---|
| 参加者（運転なし） | `registered` | `NULL` | `NULL` |
| 行きドライバー（迎え担当） | `registered` | `registered` | `NULL` |
| 帰りドライバー（送り担当） | `registered` | `NULL` | `registered` |
| 両方ドライバー | `registered` | `registered` | `registered` |

## UXフロー（最大2回の操作）
### Step 1：まず「参加」するかを選ぶ（2択）
- ボタンA：`参加者（運転なし）`
- ボタンB：`参加者（ドライバー）`

Step1で `参加者（運転なし）` を選んだユーザーは **ここで終了**（モーダルを閉じる）。

Step1で `参加者（ドライバー）` を選んだユーザーだけ Step2 に遷移する。

### Step 2：ドライバーの方向を選ぶ（3択）
- `迎えだけ（行き）`
- `送りだけ（帰り）`
- `両方（行き+帰り）`

Step2の選択後に更新を確定し、モーダルを閉じる。

## 更新（画面→DB）方針
- `参加者（運転なし）`：`participant_status='registered'`、`go_driver_status/return_driver_status` は `NULL`
- `参加者（ドライバー）`：`participant_status='registered'` を確定し、Step2の選択に応じて `go_driver_status` / `return_driver_status` を `registered` にする
- `キャンセル` の扱いは（履歴が必要なら）`cancelled` を入れる。選択UIは未登録を `NULL` として扱う。

## サーバ側の整合性（事故防止）
UIが4状態に制限していても、DBは独立列なので、サーバ側で以下の不変条件を推奨する。
- `go_driver_status='registered'` または `return_driver_status='registered'` の場合、`participant_status='registered'`
